Bloque 1 — los pasos reales. Modelar datos es casi siempre la misma secuencia, sea cual sea el dato. Primero entendés y arreglás los datos: evaluás la calidad de lo que tenés y lo limpiás — quitás o imputás faltantes (NaN) y valores inválidos, detectás filas incoherentes y las filtrás.

Después los transformás para que el modelo los pueda usar: desde conversiones de unidad (o de moneda) hasta reducción de dimensionalidad o una proyección a otro espacio. Ejemplo claro: una transformada de Fourier (FT) — pensá en una canción, que pasa de la onda de sonido en el tiempo a sus frecuencias, como las barras de un ecualizador; eso es lo que dibuja el ícono. (La FFT es solo una forma rápida de calcular la FT.)

Recién ahí, entendiendo tus datos, elegís un modelo (paso 3) — hay familias según la forma del patrón: una recta para relaciones simples, árboles para reglas y cortes, redes neuronales para patrones complejos (texto, imágenes, sonido). Después elegís sus hiperparámetros (paso 4): son las "perillas" del modelo y deciden cuánto se ajusta — de menos no ve el patrón, de más copia el ruido (la figura del paso 4). Con eso fijado, entrenás (paso 5): el modelo ajusta sus números pasada tras pasada hasta bajar el error.

Por último mirás los resultados (paso 6): comparás lo que predice cada candidato contra el valor real y medís el error. ¿Convence? Si no, cambiás de modelo o de perillas y repetís — iterás; ese es el lazo naranja, que abarca los pasos 3 a 6. Si sí, el modelo pasa a producción.

El hilo conductor — y por eso el subtítulo — es que todos los pasos apuntan a lo mismo: que el modelo encuentre el patrón en los datos. Esto es claramente un pipeline: una secuencia de pasos bien definidos con un lazo de iteración. Un software que entienda esta abstracción es muy útil — pero antes veamos cómo se hace esto hoy.

Bloque 3 — el remate. Estamos en 2026: existe la IA y existen los harnesses. Entonces existe un programa de modelado de datos que se adapta de forma custom a tu problema.

Pensalo como la relación entre una clase abstracta y la clase que la implementa; o una interfaz y su implementación; o una célula madre y una célula diferenciada — algo genérico. El objeto genérico es pluripotente pero no es útil de por sí: una clase abstracta no se puede instanciar, una función genérica necesita monomorfizarse (en dispatch estático), una célula madre no cumple una función todavía.

La IA es la herramienta de monomorfización / diferenciación de un programa de análisis que es genérico sobre los datos que tenés y el problema que querés resolver. Eso es lensing — y la próxima diapositiva muestra cómo se concreta.

Un punto del corpus no entra así al modelo. Tiene dos partes que se preparan distinto: un embedding enorme (1536 dims) y la metadata cruda en JSON. De ahí las dos columnas.

Columna izquierda — el embedding: reducción de dimensionalidad. El embedding está diseñado para capturar muchísima variabilidad, más de la que nuestro dataset realmente expresa: 1536 dims son demasiado expresivas para el problema. Las comprimimos a k dimensiones — y k es variable: lo elegís según la instancia (en spotify quedó en 64, en otra puede ser otro número).

· PCA: saca dimensiones redundantes/ruido, lo hace tratable en memoria y regulariza. Se ajusta solo con el train, no ve el test. · Autoencoder (opcional): alternativa NO lineal, aprende un latente que PCA lineal no capta — palanca que se valida por dominio (en spotify diluyó la señal; honesto). El cuánto (k) se elige desde la UI o el harness.

Columna derecha — el payload: limpieza y featurización. La metadata viene sucia y heterogénea: hay que armar columnas numéricas a partir de ella.

· Moneda: precios en distintas monedas se convierten a una sola (p. ej. AR$ → USD) para que todo sea comparable. · Imputar: un faltante no se descarta, se rellena (mediana) y se marca con un flag. · One-hot: una categoría (barrio = "Palermo") enciende una columna entre varias 0/1, sin inventar un orden falso; el vocabulario se congela y lo nuevo cae en "__other__". · log1p en el objetivo (precio): comprime la cola larga para que tres mansiones no dominen el error.

Las dos columnas convergen en una fila numérica de ancho fijo, idéntica para toda la instancia, y el manifest congela ese formulario: la copia firmada para que todo caso futuro se puntúe igual.

Quién lo ejecuta. No lo corrés a mano en una terminal. Vos lanzás el run desde la GUI o el harness, y el lensing-server es el que invoca el ejecutable (lo spawnea como subproceso) y lee su salida. La CLI es el límite entre el servidor y el predictor, no un flujo manual.

El contrato, explícito. Un predictor es un ejecutable con subcomandos. train --dataset --output --hyperparams (obligatorio): lee del dataset ya featurizado manifest.json · features.f32 · target.f32 · train/test_idx.u32 y escribe metrics.json · predictions.json · model.*.

predict --model --input --output (opcional): aplica un modelo ya entrenado a filas nuevas. export --model --output (opcional): emite un model.onnx portable.

Protocolo de stdout: una línea JSON por evento (log, epoch, …) y termina con {"event":"done"}. El servidor lee ese stream para seguir el progreso. Detalle clave del contrato: estandariza con estadísticas del train solamente — nada del test se filtra.

Consecuencia: cumplido el contrato, lo codeás en el lenguaje que sirva al problema. Hoy conviven Rust (burn), Python (XGBoost, PyTorch, scikit-learn) y Julia (Flux) en la misma instancia.

Qué es un modelo. Una definición es la receta: predictor + dataset + hiperparámetros. Cuando esa definición se entrena con éxito y la promovés, se vuelve un modelo: pesos entrenados y congelados, con un nombre y su métrica de registro.

Lo que distingue a un modelo es que ya predice: le das un ítem nuevo (sus features) y devuelve el objetivo estimado — acá, el precio. Es el artefacto reusable que después se exporta (ONNX) o se publica (showcase).

Publicar un modelo promovido como sitio. La creación está asistida por la skill /showcase y el agente showcase-builder: exportan el modelo, arman un Worker de Cloudflare independiente, resuelven los embeddings, hacen una prueba rápida de que el sitio arranca y predice (lo que en la jerga se llama "smoke test"), y dan los pasos de deploy.

Cómo se porta el modelo (qué hace ONNX). ONNX es el formato portable: el grafo model.onnx ya trae el scaler + el modelo. El bundle agrega lo que falta para ir de un ítem crudo a una predicción: featurize.json (arma el vector — PCA, one-hot, log1p, imputación, en el mismo orden que el server), pca_components.f32, input-schema.json y el manifest. Del lado del sitio, @lensing/inference + onnxruntime-web portan ese featurizer y corren el grafo en el navegador o el Worker, sin Python. La cadena: ítem + embedding → featurize → model.onnx → invertir el transform (expm1) → predicción. Para casos pesados (Pathfinder) el núcleo va en Rust → WASM.

Curado vs vivo (detalle para narrar, ya no está en la slide). El modelo no come texto, come un embedding (un vector); el sitio tiene que conseguirlo de la entrada del visitante. Dos formas: curado = horneás unos ejemplos con su embedding ya calculado y el visitante elige entre ellos — el sitio es estático, sin servicio ni clave, pero cerrado a esos ejemplos; vivo = el visitante escribe lo que quiera y el embedding se calcula en el momento llamando a un servicio (con su clave y costo) — abierto, pero depende de ese servicio. Es la decisión que tomás al publicar: galería fija y gratis, o herramienta abierta y viva. El Pathfinder de Spotify es un ejemplo de este flujo.

Tareas y artefactos

Qué produce cada tarea, y quién lo usa.

Cada flecha es un artefacto: la salida de una tarea es la entrada de la siguiente.

Fuera de este flujo: upstream-sync y upstream-contribute mantienen el código del framework, no los datos.

El flujo de artefactos. Acá no importan las etapas sino las tareas y cómo se encadenan: cada flecha es un artefacto que produce una tarea y consume la siguiente. sondea el corpus escribe domain.toml, que junto con los embeddings alimenta a construye el dataset → la matriz de features. Esa matriz, más el diseño del scan que propone el designer, son lo que corre los runs consume.

El runner es el nudo: produce tres cosas. Los reportes (experiments/*.md) los toma consolida el informe para el PDF; las métricas y modelos los toma promueve el modelo; y los PROJECT-FACTS vuelven a propone el scan — ese es el lazo (naranja). El modelo promovido alimenta el export a ONNX y el showcase, y el bundle exportado también puede ir al showcase.

Cómputo pesado

Mucho trabajo más allá de entrenar: ajustar PCA, analizar componentes, armar el bundle ONNX, convertir cada ítem en su vector de números. Es cálculo intensivo — en JS o Python sería lento.

axumConcurrencia

Tokio (runtime asíncrono) + Axum (servidor web). Rust no trae un runtime async propio — elegís cuál usar, y nosotros elegimos Tokio. Con eso todo pasa a la vez: entrenamientos corriendo, inferencia mientras se entrena, cola de tareas, la API, y el progreso de cada run llegando en vivo a la pantalla.

Compilado, runtime mínimo

Compila a un binario nativo — sin máquina virtual ni recolector de basura. No necesita un runtime instalado como Python o la JVM: un ejecutable estático que corre hasta en una imagen Docker vacía (FROM scratch) — arranca al instante, imagen mínima.

Compila a WASM

Con wasm-bindgen el código Rust compila a WebAssembly y queda llamable desde JavaScript: genera el pegamento entre ambos — el JS pasa strings, arrays y structs a través del límite y recibe tipos TypeScript ya escritos. Así el frontend invoca el mismo núcleo Rust; el featurizer es idéntico en servidor y cliente.

Por qué el core es Rust. El sistema hace mucho cálculo fuera del entrenamiento (ajuste de PCA, análisis de componentes, armado del bundle ONNX, featurización) que en JS/Python sería lento; es muy concurrente (Tokio como runtime asíncrono, Axum como servidor — entrenamientos, inferencia simultánea, cola de tareas, streams en vivo); compila a un binario nativo de runtime mínimo (sin VM ni GC, corre hasta en una imagen vacía); y compila a WASM, así que el mismo código corre en el navegador. Ese último punto es clave: el featurizer es el mismo en server y cliente, una sola fuente de verdad.

Sin runtime ni GC. Rust no tiene recolector de basura ni máquina virtual, y su runtime es mínimo (sólo el arranque y el manejo de panics). El async tampoco trae executor incorporado: elegís cuál usar — hay varios (Tokio, async-std, smol) — y nosotros elegimos Tokio. Eso da latencia predecible (cero pausas de GC) y un binario chico, justo lo que querés en un servidor bajo carga y en WASM.

Por qué importa la carga. Entrenar e inferir son cargas muy distintas: entrenar es esporádico pero intenso (mucho cómputo por un rato), mientras que inferir es liviano por request pero puede recibir muchísimos. Por eso el mismo lensing-server se corre en el rol que haga falta: hoy puede estar todo en una máquina (como en mi setup), y mañana, si la carga lo pide, separás entrenamiento e inferencia en hardware distinto. Las instancias se coordinan solo por Postgres (no comparten disco). Ver DEPLOY.md.

Crate por crate. lensing-core: la base — tipos, formato de artefactos y la config del dominio (domain.toml). lensing-pipeline: arma los datasets, del corpus Qdrant a la matriz de features (PCA + metadata). lensing-db: el estado en Postgres (definiciones, cola de runs, artefactos). lensing-onnx: un escritor de ONNX propio y sin dependencias para el export. lensing-server: el binario que junta todo (API, UI, orquestación). Los predictores van aparte: Rust (burn-mlp, burn-cnn, blend) o ejecutables externos, vía el contrato.

El modelo que corre en el navegador suele ser una versión más chica (destilada) del que entrena el server — para que entre y responda al instante. La inferencia no toca ningún servidor.

Cómo corren los showcases, por dentro. Dos motores según el peso del caso. @lensing/inference (TypeScript): porta el featurizer exacto y ejecuta el model.onnx con onnxruntime-web — alcanza para modelos tabulares/de embedding. worker-core (Rust→WASM): el mismo motor de inferencia compilado a WASM, para showcases pesados y con estado. En Pathfinder hace cuatro cosas en el navegador: embebe el item nuevo (lo vuelve un punto), busca sus vecinos (KNN) y traza una ruta con A* sobre ese grafo de vecinos, estima el score de cada track y proyecta el embedding a 3D para armar el mapa navegable — todo en el isolate de 128 MB; el stack Python/Torch/Qdrant original (~5,2 GB) no entraba.

Cómo lo accede el TypeScript. El crate se compila con wasm-pack build worker-core --target web, que con wasm-bindgen emite un paquete pkg/: el glue JS, los tipos .d.ts y el binario worker_core_bg.wasm. El worker (TS) hace import { route, search, … } from "worker-core/pkg" + import wasm from "…/worker_core_bg.wasm", lo inicializa una vez con initSync({ module: wasm }) y a partir de ahí llama las funciones Rust como si fueran TS (con tipos). wasm-bindgen se encarga del marshalling de strings y Float32Array a través de la memoria lineal del WASM. No hay servidor de inferencia: todo ocurre dentro del isolate.

Detalle: en el cliente a veces corre un modelo distinto al del server — más chico/destilado (p. ej. el proyector de arranque en frío, o un scorer horneado a ONNX por ítem) — para caber en el isolate y responder al instante.
